# Saekim 3.0.0 Release Packaging

## Build Commands

Development:

```bash
corepack pnpm tauri:dev
```

Release checks:

```bash
corepack pnpm build
cargo check --manifest-path src-tauri/Cargo.toml
```

macOS app-only bundle:

```bash
corepack pnpm tauri:build:app
```

macOS DMG bundle:

```bash
corepack pnpm tauri:build:dmg
```

`tauri:build` still uses Tauri's default target selection. The split commands are useful because a valid `.app` can be produced even when DMG creation fails on a sandboxed or headless macOS environment.

## macOS Measurement

Measured on 2026-05-20 from the 3.0.0 release packaging workstream on Apple Silicon.

| Artifact | Path | Size |
| --- | --- | ---: |
| Release binary | `src-tauri/target/release/saekim` | 18 MB |
| macOS app bundle | `src-tauri/target/release/bundle/macos/Saekim.app` | 19 MB |

`corepack pnpm tauri:build:app` completed successfully and produced `Saekim.app`. The full `corepack pnpm tauri:build` command completed the frontend build and Rust release build, then produced `Saekim.app`; the DMG packaging step failed inside Tauri's generated `bundle_dmg.sh`, so the current release gate is:

- use `corepack pnpm tauri:build:app` for local app bundle validation,
- rerun `corepack pnpm tauri:build:dmg` on the release machine before publishing,
- do not publish a DMG until the generated `Saekim_3.0.0_aarch64.dmg` exists and is measured.

## Baseline Comparison

Previous PyQt/PyInstaller baseline from the 3.0.0 backend plan:

| Artifact | Size |
| --- | ---: |
| `dist/Saekim` | about 1.0 GB |
| `Saekim.pkg` | about 416 MB |
| bundled `PyQt6` | about 416 MB |
| bundled `PyQt6/Qt6` | about 394 MB |
| bundled Chrome for Testing framework | about 206 MB |
| bundled Playwright | about 123 MB |

The 19 MB Tauri `.app` measurement is not directly comparable to a signed installer, but it confirms the runtime migration removes the largest PyQt/QWebEngine and browser-bundle costs from the app payload.

## Release Notes

3.0.0 packaging notes should state:

- The runtime is Tauri plus the system WebView.
- PDF export uses the operating system print dialog.
- PDF-to-Markdown import is deferred from the 3.0.0 MVP.
- macOS artifacts are currently unsigned and unnotarized unless a signing identity is configured at release time.
- Windows builds must be produced on Windows and must verify WebView2 availability.

## Smoke Test

Before publishing a 3.0.0 build:

- launch the app bundle,
- open a folder,
- expand nested folders,
- open, edit, save, and save-as a Markdown file,
- verify session restore after restart,
- switch theme and view mode,
- render code, Mermaid, and KaTeX samples,
- export through the print dialog,
- confirm PDF import shows the documented unsupported state if wired to UI later.
